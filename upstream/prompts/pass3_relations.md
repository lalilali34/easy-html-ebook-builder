# pass3 · 块间关系

## 本轮任务

**只看功能块列表**，不重新分析内容，判断块与块之间是什么逻辑关系。

## 输入字段

- `blocks[]`：只含 `id`、`time_range`、`function`、`summary` 的功能块列表（来自 pass2）。

## 输出字段

```json
{
  "relations": [
    { "from": "b1", "to": "b2", "type": "因此" },
    { "from": "b2", "to": "b3", "type": "例如" }
  ]
}
```

- `from` / `to` 必须是输入里真实存在的块 id。
- `type` 只能从封闭集合选，语义固定：
  - `因此`：from 推出 to；
  - `但是`：from 与 to 构成转折；
  - `例如`：to 是 from 的例子；
  - `依赖`：from 的解释依赖 to；
  - `反驳`：from 反驳 to 的观点；
  - `铺垫`：from 为 to 预备。
- 不要求全连接；只写能确证的边。同一条边不得重复。

## 依据与方向（强制）

1. 不要只按时间相邻连边。每条边必须能在 `from` 和 `to` 两个子块的 `summary` 里找到明确依据；找不到依据的边不要建。
2. 「反驳」要求 `from` 块的 `summary` 能指出 `to` 块被反驳的具体内容；只写「反驳了对方观点」不算依据。
3. 禁止输出 `type = 过渡`。schema 的 `relations.type` 只有六种：因此、但是、例如、依赖、反驳、铺垫。
4. 「依赖」方向定义：`from → to` 表示 `from` 块的论证需要 `to` 块作为前提或基础。如果 `to` 为 `from` 提供例子，用「例如」；如果 `to` 为 `from` 铺垫背景，用「铺垫」；如果 `from` 为 `to` 提供前提，方向应为 `to → from` 依赖，不要写反。
   示例：定义块 A 为理由块 B 提供概念前提，应写 `B → A` 依赖，不是 `A → B` 依赖。

## 禁止事项

- 禁止新增块、改块的功能标签、改块的时间。
- 禁止写 `purpose`、`basis`、`author_says`、`my_*`、`recap`。
- 禁止为了"看起来完整"而给每个块补边；边必须有原文依据（可由两块的 function + summary 判断）。
- 禁止输出 JSON 以外的任何文字。
